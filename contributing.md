# Contributing

Thanks for your interest in Skynet.

**VEAF maintains this project.** The [Regroupement's
repository](https://github.com/regroupement-patrouille/Skynet-IADS) is read-only and
[walder's](https://github.com/walder/Skynet-IADS) has been inactive for years; the two communities
agreed that VEAF takes it over. So this is where issues, discussions and pull requests belong — not
upstream.

Before spending time on a feature, propose it: open an issue, or bring it to the
[VEAF Discord](https://discord.gg/veaf). Feedback before code saves more time than it costs.

## What you need

- **Lua 5.1.** The deliverable runs inside DCS, which is Lua 5.1 — no `goto`, no `<const>`, no
  `table.move`, no `utf8.*`. The standalone test suite refuses to run on anything else.
- **PowerShell**, for the build. `pwsh` (PowerShell 7) works on every platform.
- **DCS** is *not* required for most contributions. It used to be: the whole test suite lived
  inside a mission. Logic is now testable on a plain Lua interpreter, and DCS is only needed for the
  in-sim suites and for checking behaviour you cannot assert without the simulator.

## Layout

| | |
|---|---|
| `skynet-iads-source/*.lua` | **the sources.** This is what you edit |
| `demo-missions/skynet-iads-compiled.lua` | **a build artifact.** Generated by the build, never edited by hand |
| `test/lua/` | the standalone Lua 5.1 test suite |
| `unit-tests/*.miz` | the legacy in-sim suites, being migrated to `test/lua/` |
| `build-tools/` | the build script and its helpers |
| `.backlog/` | what is planned, in progress and done |
| `docs/evolutions.md` | ideas and things noticed in passing, not yet committed work |

## Git flow

- `develop` is the default branch and the target of every pull request. `master` carries releases.
- Branch from `develop`: `feature/<something>` or `fix/<something>`. Never commit directly to
  `develop` or `master`.
- One branch and one pull request per lot, not per ticket.
- [Conventional Commits](https://www.conventionalcommits.org/), in English.
- Branches are deleted on merge — this is automatic.

## Everything in English

Code, comments, commit messages, pull requests, documentation. This project has users beyond the
French-speaking community.

## Test first

Write the failing test, make it pass, then refactor. It takes a little longer the first time and
saves the afternoon you would otherwise spend re-testing everything by hand after a two-line change.

### Two suites, two jobs

| Suite | Runs where | For what |
|---|---|---|
| `test/lua/` | plain Lua 5.1 — `lua5.1 test/lua/run.lua`, and in CI on every pull request and on pushes to `develop` and `master` | **logic**: state machines, parsing, arithmetic, branching. No DCS. **New logic tests go here.** |
| `unit-tests/*.miz` | inside DCS — launch the mission, read `dcs.log` | **functional**: what genuinely needs the simulator — terrain elevation, real radar detection geometry, in-game events |

A suite name filters: `lua5.1 test/lua/run.lua contact` runs the suites whose filename contains
`contact`.

To add a standalone test, create `test/lua/test_<module>.lua` that pulls in `luaunit.lua` and
`dcs-stub.lua`, loads the source module through `skynet-loader.lua`, and ends with
`os.exit(luaunit.LuaUnit.run())`. `test/lua/test_skynet_iads_contact.lua` is the pattern to copy,
and `test/lua/README.md` explains how to run it.

**One warning about the stub.** A test that passes only because `dcs-stub.lua` returns something
convenient proves nothing. When your test needs the stub extended, extend it deliberately, and write
down which real DCS behaviour it stands in for.

Do not open a pull request with tests failing.

## Building

From the `build-tools` directory, with the version as the only argument:

```powershell
cd build-tools
pwsh -File ./build-compiled-script.ps1 3.5.0
```

Two things to know, because both have bitten people:

- **The version argument is mandatory.** Without it the script prints `No Version supplied, not
  bulding script` and stops. The version it receives is stamped into the artifact's first line,
  along with the build date — that banner is how anyone identifies what a mission is running.
- **The script uses relative paths.** Run it from `build-tools`, not from the repository root.

What it produces:

1. `demo-missions/skynet-iads-compiled.lua`, the concatenation of every source file in load order;
2. `README.md` at the root, regenerated from `skynet-iads-source/README_source.md` with a table of
   contents substituted into `{TOC_PLACEHOLDER}`.

### The README is generated

**Never edit `README.md`.** Edit `skynet-iads-source/README_source.md`; the build rewrites the root
file from it.

The table of contents comes from `build-tools/bin/gh-md-toc.exe`, which **needs network access** —
and is a Windows binary, so it will not run on a Linux CI runner as it stands. On failure the build
now bails rather than silently replacing the table of contents with a blank line.

## Versioning

[Semantic versioning](https://semver.org/). A change to what a mission sees at runtime is at least a
minor.

Two numbering schemes coexisted for years — inherited tags stopping at `v2.0.1` from walder's
lineage, and the artifact calling itself `3.4.0RP-VEAF`. Settled on 2026-09-19: VEAF continues the
**artifact's** lineage, because that is the number people read in a log. The first VEAF release is
**3.5.0**, tagged `v3.5.0`, and the `RP` suffix is dropped.

## Changelog

Every pull request that changes `skynet-iads-source/` adds an entry to `CHANGELOG.md`, appended at
the **end** of the `[Unreleased]` section.

This is not bookkeeping. The main consumer of this project is another repository —
[VEAF-Mission-Creation-Tools](https://github.com/VEAF/VEAF-Mission-Creation-Tools) copies the built
artifact into the missions it produces — and the changelog is how they know whether a new build is
worth taking. That copy has run a month behind without anyone noticing.
